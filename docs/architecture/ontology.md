# ThingOS Canonical Typed-World Ontology

> **Status**: Authoritative constitutional reference — Phase 9 baseline.
>
> This document is the single source of truth for the core typed-world
> concepts in ThingOS.  All new system design, kernel changes, and review
> decisions are conducted against these definitions.  When compatibility
> vocabulary (`process`, `fd`, `signal`, `session`, …) appears in new code,
> this document provides the canonical alternative.

## Purpose

ThingOS is a **typed world**: every meaningful element of the running system is
a first-class object with a declared kind, a stable identity, and explicit
relationships.  This document establishes the seven core concepts and the rules
that govern them.

The goal is to make typed-world design **enforceable rather than atmospheric**.
A reviewer consulting this document should be able to answer "what canonical
concept owns this meaning?" for any proposed change.

## 1. Core Concept Definitions

---

### 1.1 Thing

**What it is**

A `Thing` is any first-class object in the ThingOS typed world.  Every
discrete entity the system manages — a file, a device, a running executable, a
message, a capability token — is a `Thing`.  All Things have a `Kind` that
describes their structure and valid operations.

**What it is not**

A `Thing` is not a Unix "file" or "process".  Those are compatibility
projections of Things (see §3.1, §3.4).  A `Thing` is not an amorphous blob of
bytes; it carries typed structure determined by its `Kind`.

**What it owns**

- A stable identity (128-bit ThingId derived from its `Kind`).
- Zero or more `Form` projections (how it is expressed in a given context).
- Membership in zero or more `Place` contexts (where it is visible).

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| has | `Kind` | Every Thing declares exactly one Kind |
| expressed as | `Form` | A Thing may be projected into multiple Forms |
| visible in | `Place` | A Thing is accessible within one or more Places |
| referenced by | `Authority` | Authority determines who may act on a Thing |

**Code status**: `KindClass::Thing` in `thingos::KindClass`.  The term appears
throughout the kernel VFS (`IpcThing`, `VfsNode`) where Unix "files" and "fds"
are the current compatibility surface over Thing access.

---

### 1.2 Kind

**What it is**

A `Kind` is the authoritative definition of structure and meaning for a class
of Things.  It answers: *what is this?*  A `Kind` specifies field layout,
valid operations, compatibility invariants, and schema version.  Everything
that crosses a system boundary declares its Kind.

**What it is not**

A `Kind` is not a runtime instance; it is a schema.  A `Kind` is not a C
struct or Rust type definition — those are artefacts generated *from* a Kind.
A `Kind` is not a MIME type or content-type header; those are compatibility
projections of Kind identity.

**What it owns**

- A unique stable identifier (128-bit KindId, generated by `kindc`).
- A canonical binary layout (the default `Form`).
- Zero or more additional `Form` definitions (debug text, JSON bridge, etc.).
- Version history and compatibility rules.

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| describes | `Thing` | Every Thing is an instance of exactly one Kind |
| produces | `Form` | A Kind may have multiple Form representations |
| referenced by | `Authority` | Authority may grant or deny operations per Kind |

**Code status**: Canonical.  `KIND_ID_*` constants in every `thingos::*`
module are generated by the `kindc` schema compiler in `tools/kindc/`.  The
`KindClass` enum in `thingos::lib` provides a coarse kind taxonomy.

---

### 1.3 Form

**What it is**

A `Form` is a representation or projection of a `Kind`.  It answers: *how is
this Thing expressed?*  A Kind may have multiple Forms; each Form serialises
the same underlying meaning differently for a particular context or consumer.

**What it is not**

A `Form` is not a different `Kind`.  A Form change does not change what a
Thing *is*; it changes how that Thing appears.  A `Form` is not a schema
version change (schema versions are a `Kind` concern).

**What it owns**

- A declared encoding (binary, text, JSON, procfs text, …).
- A mapping from the canonical `Kind` field layout to the encoding.

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| represents | `Kind` | Every Form belongs to exactly one Kind |
| exposed by | `Place` | A Place may surface a Thing through a particular Form |

**Code status**: Canonical in concept.  Current Forms in use:

| Form | Example | Notes |
|---|---|---|
| Canonical binary | IPC message payload | Default Form; what `kindc` generates |
| procfs text | `/proc/<pid>/place`, `/proc/<pid>/authority` | Debug/introspection Form |
| JSON | `kindc` fixture output | Bridge Form for tooling |

A VFS path that returns the canonical binary encoding of a Thing is that
Thing's binary Form; `/proc/<pid>/place` returning a text blob is its text
Form.

---

### 1.4 Place

**What it is**

A `Place` is the canonical world-context in ThingOS.  It is the explicit
answer to: *in what world does this execution occur?*  A Place captures the
visibility boundaries and mount/namespace view that define where a running unit
lives — independent of *who* is running it (`Authority`) or *how* it is
coordinated (`Group`).

**What it is not**

A `Place` is not a Unix process, directory, or container.  Those are
compatibility projections.  A `Place` is not a scheduling unit (`Task`) and is
not a lifecycle unit (`Job`).  A `Place` is not a security boundary by itself;
that is `Authority`.

**What it owns**

- Current working path (`cwd`) — the active position within the VFS view.
- Namespace label — which VFS mount table this Place uses.
- Root path — the apparent filesystem root for path resolution.

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| contains | `Thing` | Things are visible and accessible within a Place |
| inhabited by | `Person` (via `Presence`) | A Person enters a Place through a Presence |
| backed by | `Authority` | Authority determines what operations are permitted within a Place |
| projects | `Form` | A Place may surface Things through specific Forms (e.g. pathname as a Form of Thing address) |

**Code status**: Canonical.  `thingos::place::Place` (Phase 8).  Backed
transitionally by `Process::cwd` / `Process::namespace` through
`kernel::place::bridge::place_from_snapshot`.  Exposed as a procfs text Form
at `/proc/<pid>/place`.

---

### 1.5 Person

**What it is**

A `Person` is the canonical actor in ThingOS.  It represents an entity —
human user, automated agent, or service identity — that can act upon Things.
A Person does not act directly; it acts *through* an `Authority` and *inhabits*
a `Place` via a `Presence`.

**What it is not**

A `Person` is not a Unix uid/gid tuple.  uid/gid are compatibility projections
of Person identity onto the POSIX permission model.  A `Person` is not a
process; a process is a compatibility projection that may carry a Person
context.  A `Person` is not a session; a session is a compatibility projection
of Presence into Unix TTY semantics.

**What it owns**

- A stable identity (ThingId, 128-bit).
- A kind (Human, Agent, or Service — from `tools/kindc/fixtures/generated`).

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| acts through | `Authority` | A Person's operations are mediated by an Authority context |
| inhabits | `Place` (via `Presence`) | A Person is situated in a Place through a Presence record |
| identified as | `Kind` (`thingos.person`) | Person identity is a typed object, not a raw integer |

**Code status**: Canonical in definition.  `PersonKind` (Human, Agent,
Service) in `tools/kindc/fixtures/generated/mod.rs`.  Not yet a first-class
kernel object; Person identity is currently transitionally carried as a name
string inside `Authority`.  Full extraction (uid/gid → typed PersonId,
service-account binding) is deferred to Phase 9+.

---

### 1.6 Authority

**What it is**

`Authority` is the canonical permission context in ThingOS.  It is the
explicit answer to: *under what power does this action occur?*  An Authority
carries the credentials, capability strings, and rights scope that determine
what operations a running unit may perform.

**What it is not**

An `Authority` is not a Person.  A Person *has* or *acts through* an Authority,
but Authority is the power context, not the identity.  An `Authority` is not a
security label; labels are a compatibility projection.  An `Authority` is not
a scheduling policy; that belongs to `Task`.

**What it owns**

- A canonical name for this authority context.
- A capability string list (active rights).
- (Future) uid/gid-like identity fields, delegation chains, service-account
  bindings.

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| held by | `Person` | A Person acts under an Authority |
| governs access to | `Thing` | Authority determines who may read/write/invoke a Thing |
| scoped within | `Place` | Authority and Place interact to determine the effective permission set |
| grants/denies per | `Kind` | Authority checks may be Kind-specific |

**Code status**: Canonical.  `thingos::authority::Authority` (Phase 7).
Backed transitionally by `ProcessSnapshot::name` through
`kernel::authority::bridge`.  Exposed as a procfs text Form at
`/proc/<pid>/authority`.

---

### 1.7 Presence

**What it is**

`Presence` is the canonical deferred embodiment model in ThingOS.  It is a
structured description of *where and how* an entity is situated within the
system's social and spatial context.  A Presence record says: "this subject
(Person or agent) is present in this Place, in this Group, with this mode of
embodiment, as of this timestamp."

**What it is not**

A `Presence` is not a scheduler primitive or execution-residency concept.
A `Presence` is not a Unix session; Unix sessions are compatibility projections
of Presence into TTY attachment semantics.  A `Presence` is not a live
occupancy sensor or device-fusion result.  A `Presence` is not an authority
boundary (that is `Authority`).

**What it owns**

- Subject reference (`EntityRef` — opaque 128-bit Person or agent ThingId).
- Place reference (optional — where the subject is present).
- Group reference (optional — coordination group anchoring the presence).
- Mode (`Active`, `Latent`, `Remote`, `Projected`, `Deferred`, `Unavailable`).
- Embodiment kind (`Direct`, `Remote`, `Inherited`, `Symbolic`, `Deferred`).
- Observed-at timestamp (when this record was last known valid).

**Relationships**

| Relation | Target | Notes |
|---|---|---|
| situates | `Person` in a `Place` | Core purpose: link an actor to a world-context |
| anchors in | `Group` | Presence may be anchored to a coordination group |
| derives from | `Authority` | Presence does not duplicate Authority; they compose |
| expresses | `Mode` | The quality of situated existence |

**Code status**: Canonical / Emerging.  `thingos::presence::Presence` schema is
stable (Phase 8).  Runtime embodiment integration is deliberately deferred
until Place and Group foundations are complete.  The controlling-TTY
relationship (Unix `session`/`setsid`) maps to Presence — see §3.5.

## 2. Architectural Rules

The following rules apply to all code in `kernel/`, `abi/`, `bran/`, `stem/`,
and `userspace/`.  They are not guidelines; they are constraints.

### Rule 1 — New meaning is introduced in typed-world terms first

When a new OS capability is designed, it is specified using the canonical
vocabulary (`Thing`, `Kind`, `Form`, `Place`, `Person`, `Authority`,
`Presence`, `Group`, `Job`, `Space`, `Task`, `Message`) before any
Unix-compatible surface is defined.  The Unix projection, if any, is a
secondary derivation.

### Rule 2 — Compatibility concepts do not define system truth

A Unix concept (`process`, `fd`, `pathname`, `signal`, `session`, …) is always
a projected view of one or more canonical typed-world objects.  The canonical
object exists independently of whether a Unix projection is exposed.  The
projection is never the definition.

### Rule 3 — Reviewers reject new architectural concepts in Unix-only terms

If a proposed change introduces new system meaning that can only be described
in Unix vocabulary, the change must be reworked at the typed-world level before
any implementation proceeds.

### Rule 4 — Bridges are transient and bounded

Every compatibility projection lives in a named bridge module
(`kernel::{concept}::bridge`).  Bridges are expected to shrink as canonical
objects mature.  A bridge that grows is a regression.

### Rule 5 — Ontology is the design review anchor

The question "what canonical concept owns this meaning?" must have a clear
answer from this document for every piece of new state or behavior introduced
by a change.  If the answer is "none of the above", the concept must be
proposed as an addition to this document or an existing concept must be
extended — before the implementation lands.

## 3. Worked Examples from Current Code

The following examples map real subsystems into the ontology.

---

### 3.1 VFS node as one Form of Thing access

A VFS node (`kernel::vfs::VfsNode`) is the current compatibility representation
of a `Thing` within a `Place` (the mounted filesystem tree).

| Typed-world view | Code reality |
|---|---|
| A `Thing` with a `Kind` | The object behind the VFS path (file, device, directory) |
| The VFS path | One `Form` of the Thing's address within a `Place` |
| `open()` returning a file descriptor | An integer handle to one `Form` of Thing access |
| `read()` / `write()` | Operations on the Thing mediated by the caller's `Authority` |

The `IpcThing` type in `kernel::ipc` is the kernel-internal reference that
will eventually become a first-class typed handle (`Handle`) — a replacement
for the Unix fd integer that carries Kind information.

---

### 3.2 Process as a compatibility projection

A Unix `process` is not a canonical typed-world concept.  It is a compatibility
projection that bundles five orthogonal canonical objects:

| Canonical object | Unix process field |
|---|---|
| `Job` | Lifecycle (creation, exit, reaping) |
| `Space` | Address-space and page-table state |
| `Authority` | Credentials, capabilities, effective uid/gid |
| `Place` | Working directory, namespace, root path |
| `Task`(s) | One or more schedulable execution units |

The kernel's `Process` struct (in `kernel/src/task/mod.rs`) is the transitional
backing.  All five canonical objects are extracted from it through dedicated
bridge modules and exposed as first-class typed objects at the public API
surface.  New system semantics must not be added to `Process` directly; they
belong to one of the five canonical owners above.

---

### 3.3 File descriptor as one reference Form for a Thing

A Unix file descriptor (`fd`) is an integer index into the process fd table.
In typed-world terms it is:

- a reference to a specific `Form` of a `Thing` (the open file/device/socket),
- scoped within the `Place` of the calling execution unit,
- governed by the caller's `Authority` (read/write/exec permissions),
- a compatibility surface maintained in `Process.fd_table` (quarantined in
  `ProcessUnixCompat`).

The planned replacement is `Handle` — a typed, capability-carrying reference
that exposes the Kind of the underlying Thing.  Until `Handle` is introduced,
fd integers remain the compatibility surface.

---

### 3.4 Signal delivery as a projection over Group + Authority + Message

A Unix signal encodes three orthogonal typed-world concerns:

| Signal aspect | Canonical owner | Example signals |
|---|---|---|
| Job-control (stop/continue) | `Group` (Foreground kind) | SIGTSTP, SIGCONT, SIGTTIN, SIGTTOU |
| Permission to send | `Authority` | `kill(-1, sig)` requires authority |
| Asynchronous notification | `Message` (typed event envelope) | SIGUSR1, SIGUSR2 |

Currently all three aspects are quarantined in `Process.unix_compat.signals`
(`ProcessSignals` / `ThreadSignals`) because the canonical owners are not yet
fully live.  Every call site that touches `unix_compat.signals` is a visible
signal that typed-world replacement work is outstanding.

---

### 3.5 Session / TTY attachment as a Presence concern

In Unix, a "session" is the binding between a process group and a controlling
terminal.  In typed-world terms:

| Unix concept | Canonical owner | Notes |
|---|---|---|
| Session identity (`sid`) | `Group` (Foreground kind) | Group anchors the coordination domain |
| Session leader | `Job` | The Job whose exit dissolves the Group |
| Controlling TTY | `Presence` | Terminal attachment is a situated relationship between a Person and a Place |
| `setsid` / `tcsetpgrp` | Future `SYS_TTY_ATTACH` → `Presence` mutation | Not yet canonical |

The `devfs::ConsoleTtyState::controlling_sid` field is the current
compatibility backing.  It is quarantined and will migrate to a `Presence`
record once Presence runtime integration is introduced.

## 5. How to Use This Document in Design Reviews

1. **Identify the canonical owner.** For every new piece of state or
   behaviour, ask: which of the seven core concepts (or their derived concepts
   `Group`, `Job`, `Space`, `Task`, `Message`) owns this?

2. **Check the status.** Consult §4 and
   `docs/architecture/concept-classification.md`.  If the concept is
   Canonical, use it freely.  If Transitional, mark uses `// PROVISIONAL:`.

3. **Verify the bridge.** If the backing implementation is still inside
   `Process` or a Unix-shaped struct, confirm that access goes through the
   corresponding bridge module, not through direct field reads.

4. **Apply Rule 3.** If the change introduces new meaning that can only be
   articulated in Unix vocabulary, require a typed-world redesign before
   approving.

5. **Update this document.** If a review surfaces an unanswered "what concept
   owns this?" question, open an issue or PR to add the answer here before the
   implementing change lands.
