# Scheduler Migration Architecture Map (Migration 12/12)

This note is the ownership map for scheduler migration work. It defines what is
canonical truth, what is runtime cache, what is compatibility projection, and
what scheduler code is allowed to know.

## 1) Canonical generated kinds

Canonical schema truth is generated by `kindc` into
`thingos/src/kinds/generated/mod.rs` (see header: “canonical source of
Kind-derived types”).

Scheduler-adjacent canonical identities and records:

- `thingos::kinds::{TaskId, JobId, GroupId, SpaceId}`
- `thingos::kinds::ThingId` (schema object references)
- `thingos::kinds::{Task, TaskState, Job, JobState, Group, Space}`

Canonical kind guidance is owned by `tools/kindc/kinds/*.kind` and explicitly
forbids encoding scheduler hot-path cache fields in schemas.

## 2) Runtime bridges

Runtime bridges project canonical data into runtime/scheduler shapes without
changing ownership:

- `kernel/src/sched/bridge.rs`
  - Canonical input: `thingos::task::Task`
  - Runtime projection: `TaskRuntime`, `SchedulableRuntime`
  - Hot-cache projection: `TaskSchedCache` → `state::TaskSchedFields`
- `kernel/src/task/identity.rs`
  - Explicit identity mapping helpers between runtime IDs, canonical IDs, and
    Unix compatibility IDs.
- `kernel/src/sched/hooks.rs`
  - `ProcessSnapshot` is a mixed projection envelope for procfs and compat
    readers; it is not canonical schema truth.

Bridge rule: flow is one-way from canonical/generated intent into runtime/cache
projections. Scheduler cache never becomes schema truth.

## 3) Hot scheduler cache

Hot scheduler cache lives in `kernel/src/sched/state.rs`:

- `ThreadSchedFields` (alias `TaskSchedFields`)
- Run-queue placement and per-CPU scheduler structures (`runq_location`,
  per-CPU `runq`, `current`, `need_resched`)

This layer is performance-oriented dispatch state. It mirrors selected runtime
task fields plus scheduler-only queue metadata, and is synchronized by scheduler
mutation paths.

## 4) Unix compatibility projection

Unix-facing IDs and surfaces are compatibility projection only:

- Compatibility IDs: `pid`, `pgid`, `sid` (`u32`)
- Snapshot/process compatibility fields in `ProcessSnapshot` and
  `Process.unix_compat`
- Compatibility APIs (`waitpid`, process listing/status style views)

These fields must not be treated as canonical ownership for lifecycle, group,
space, or scheduler semantics.

## 5) Identity mapping (runtime ↔ canonical ↔ compat)

Identity mappings are explicit in `kernel/src/task/identity.rs`:

- Runtime task ID (`ThreadId`/`RuntimeTaskId`) ↔ canonical `TaskId`: 1:1 mapping
- Compatibility `pid` → canonical `JobId` (transitional mapping)
- Compatibility `pgid`/`sid` → canonical `GroupId` (transitional mapping)
- Runtime `thingos::space::SpaceId` wrapper → canonical `SpaceId`
- Leader-only compatibility mapping: `pid` ↔ leader `TaskId`

No ad hoc casts should be introduced outside these helpers.

## 6) Lifecycle ownership

Lifecycle semantics are canonical `Job` ownership (see `docs/architecture/job.md`):

- Parent/child lineage
- Exit and wait/reap semantics
- Group-level lifecycle continuity / exec gating

Scheduler owns dispatch mechanics (runnable/running/blocked/dead transitions and
run-queue execution), not lifecycle ontology.

## 7) Data ownership by layer (canonical map)

| Layer | Primary data | Owner | Reads from | Writes to | Not allowed to own |
|---|---|---|---|---|---|
| Canonical schema | Kind records and stable IDs (`Task/Job/Group/Space`, `ThingId`) | `kindc` output (`thingos::kinds::generated`) | `.kind` definitions | Generated Rust types | Scheduler-local hot cache fields |
| Runtime bridge | Projection structs (`TaskRuntime`, `SchedulableRuntime`, identity mapping) | `kernel::{sched::bridge, task::identity}` | Canonical + runtime backing | Runtime/cache projections | New semantic truth |
| Scheduler hot cache | `TaskSchedFields`, run-queue placement, per-CPU dispatch state | `kernel::sched::state` | Runtime task state via bridge/mutation paths | Dispatch-critical cache + queue metadata | Job/Group/Space/Unix ontology |
| Unix compatibility projection | `pid/pgid/sid`, process snapshot compat fields | `Process.unix_compat`, `sched::hooks::ProcessSnapshot` | Canonical/runtime state | Unix-facing projected views | Canonical ownership claims |

## 8) Review answers for new contributors

- **What is canonical truth?**  
  Kind-generated schema records and IDs (`thingos::kinds::generated`) plus
  canonical object definitions (`Task/Job/Group/Space`).
- **What is runtime cache?**  
  `TaskSchedFields` and scheduler queue metadata in `kernel::sched::state`.
- **What is projection?**  
  Bridge/snapshot outputs (`sched::bridge`, `task::identity`, `sched::hooks`)
  that adapt canonical/runtime data for dispatch or compatibility consumers.
- **What is scheduler allowed to know?**  
  Dispatch-critical task state and queue metadata only; scheduler must not own
  canonical lifecycle/group/space truth or reinterpret Unix compatibility fields
  as architecture truth.
